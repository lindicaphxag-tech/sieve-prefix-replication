# 准入侧门控：一次诚实的负结果（WVC 的 W1 实测）

WVC 的第二条腿是“共享感知准入”：当 KV 空间紧张且某个等待请求的前缀与常驻缓存重合度低时，推迟它的 prefill，优先放行已经命中的请求。本文件记录这次尝试的全部实现与结果，包括它为什么失效。

## 实现

在 `vllm/core/scheduler.py` 的 `_schedule_prefills` 中，于“已缓存 token 数 / 未缓存 token 数”计算之后插入判定：若条件成立，把该请求放回 `leftover_waiting_sequences` 并 `continue`，即跳过它去看队列里的下一个请求。为了避免饥饥，若整条等待队列都会被推迟，则强制放行队首。关闭开关（`WVC_GATE=0`）时行为与基线一致（已用同一配置复跑验证：命中率 0.1064，无 `[wvc]` 输出）。

判定需要三个量：真正空闲块占比、已缓存前缀占用占比、该请求的常驻前缀比例。三次迭代分别用了三种压力信号：

1. **`get_num_free_gpu_blocks()` / total**（阈值 15%）→ 从未触发。
2. **`_cached_blocks` 占用 / total**（阈值 30%）→ 从未触发。
3. **`_hashless_allocator.get_num_free_blocks()` / total**（阈值 12%，即“几乎没有任何崭新块”）→ 从未触发。

## 为什么触发不了

vLLM 的 `get_num_free_blocks()` 把“可被淘汰的已缓存块”算作空闲，从调度器视角池子永远不满。真正约束 prefill 的不是空闲块数，而是分配失败：`can_allocate` 失败时调度器直接 break，等待队列原地不动。也就是说，**准入侧早就被 vLLM 自己的块可用性阻塞隐式实现了**；“一次性请求冲掉共享前缀”这件事在调度器的准入点上是不可见的，它只表现为分配器内部的淘汰抖动。

因此在本机这个规模上（1733 blocks、12 GB 配额、并发 16/32），唯一的有效杠杆是**受害者选择**，这正是 LFU-W 站的位置。W1 的操作形态必须在分配器内部，而不是调度器内部。

## 关于吞吐的更正

同一配置（conversation c16、LRU、无门控）在本机上复跑得到 63.09 / 64.77 / 50.60 req/s 三个值，跨度 27%：这台卡与他人常驻任务共享，吞吐受邻居影响，不能用来判断插桩的代价。因此本节只能得出：**命中率上没有任何可观测变化**；吞吐差异不可归因。原先“插桩 −11%”的说法不成立，撑回。要量化插桩开销必须在独占卡上重做。

## 对框架的修订

- W1 保留为**分析判据**（解释策略效应为何随 σ、κ 变化），但**不作为调度器侧的执行机制**；
- W3 门禁的判断依据改为“机制是否在分配器内部”：窗口外退回 LRU，窗口内用 LFU-W，两条都在分配器里；
- 准入与淘汰的联合优化留给 2028 的 disaggregated prefill——那里准入决策发生在块分配之前，W1 才有落点。
