# 路由器：把"选策略"做成前端估计 + 分配器执行（2026-11-24）

分配器内部看不到 session，所以 TeW 在三个真机负载上代理量恒低于阈值、退化为 LRU（`PAPER.md` §3.8）。本文件把估计器搬到**请求流侧**（前置服务能看到 prompt 前缀与血缘），分配器只负责执行被选中的受害者规则，然后用本地三条 trace 做**因果**（不使用未来信息）验证。

## 机制

前端每 256 请求一个窗口维护三个量：

- **σ̂**：本窗口内观察到的复用访问中，上次访问者属于**不同血缘**的比例。血缘用"与最近 64 个请求共享前 4 块"的最长前缀归并（与 `reuse_profile.py` 同一规则）。
- **λ̂**：本窗口新增块的速率（块/请求）。
- **ĝ**：本窗口跨血缘复用的平均间隔（请求数）。

判据：`σ̂ ≥ 0.25` 且 `ρ̂ = C / (λ̂ · ĝ) ≥ 0.40` 时，分配器切到 SIEVE；否则 LRU。ρ 是"池能否活过一次复用间隔"的估计，替换了 v4 里那个在 trace 侧无法定义的 κ。

实现：`router_sim.py`（本文件同目录），`python3 router_sim.py --capacity 1733`。

工作点（1733 blocks = 真机同容量）：

- 路由器 **0.1121**，LRU 0.0980 → **+14.4% 相对增益**，把该工作点可达的 +2.49 pp 拿到了 **1.41 pp（57%）**，且**没有一次窗口是负收益**（400 blocks 时 SIEVE 本来只赢 0.27 pp，路由器正确留在 LRU）。
- 代价是"上限只有 SIEVE"：800/1200 上 LFU-W 更强（0.0836/0.0910），路由器没能切过去，这部分损失占全部 regret 的主体。事后最优 0.1277 说明还有 1.56 pp 可挖。

## 边界（必须一起读）

1. 血缘是代理：与 `reuse_profile.py` 同规则，需要在前端对 prompt 前缀做哈希。真机里 session id 直接可得，代理只用于 trace 回放。
2. 阈值（0.25 / 0.40）是按 v4 定律先验写定的，**没有在验证集上调过**；换负载需要重校，这正是 2027 的开放问题。
3. 路由器只做 LRU↔SIEVE 二选一，因此 regret 的上界是 LFU-W 与 SIEVE 的差。改成三选一（把 LFU-W 作为"高 σ̂ 高 ρ̂"分支）是明确的下一个实验。
4. 本地 trace 无时间戳，ĝ 与 λ̂ 都按请求计；生产侧可按微秒算，两者不可直接比。
5. 回放模型与 `offline_sim.py` 相同：请求按前缀链插入、trim 到容量、无 pinning，因此绝对值低于真机，只比排序。
